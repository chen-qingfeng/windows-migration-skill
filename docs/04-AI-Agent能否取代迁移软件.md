# 如果让 AI Agent 来做：能不能省掉"开发软件 + 商用上线"

> 2026-11 ｜ 第四份：**前瞻判断**
> 问题：能不能不做一个商业软件，直接靠一个 AI Agent 把这件干完？

---

## 0. 一句话

> **"做软件"的成本确实正在塌缩，"承担责任"的成本没有。**
> AI 进步的是"知道怎么做"，没进步的是"出了事谁负责"。前者正在变成公共品，后者仍然是需要一家公司去承担的东西。

---

## 1. 先承认：这件事的 70% 确实正在被 Agent 吃掉

我上一份文档里说，你的护城河是"几千个应用的配方库，要 18–24 个月人工积累"。

**这个判断在 Agent 面前是站不住的。** 一个大模型 + 联网搜索，本身就是一个活的配方库：

- 它知道 `%APPDATA%\Cursor\User\settings.json` 在哪；
- 它能查出某个软件的静默安装参数；
- 它能读懂安装日志、能改脚本、能试错重来。

**你花两年攒的数据，模型已经大致有了。** 这一条必须先认，否则后面的判断全是自欺。

### 逐环节的诚实评估

| 迁移环节 | Agent 今天 | 2 年后 | 说明 |
|---|:-:|:-:|---|
| ① 发现装了哪些软件 | ● 能 | ● 能 | 跑 PowerShell、读注册表、查 winget，纯信息活 |
| ② 判断"这是什么、该怎么装" | ● 能，且**强于人工配方库** | ● 强 | 这是 LLM 的主场：常识 + 联网 |
| ③ 生成安装/迁移脚本 | ◐ 能，但需人审 | ● 能 | 一次生成，错了再改 |
| ④ 跨机传输大文件 | ● 能 | ● 能 | 它只是调 robocopy/rsync 的调度员 |
| ⑤ 推断配置路径 | ◐ 约 80% 准 | ● 90%+ | 剩下 20% 靠试错和日志 |
| ⑥ 执行 GUI 安装（UAC、弹窗、下一步） | ○ 弱 | ◐ 中 | 除非有 computer-use，否则卡在图形界面 |
| ⑦ **验证与修复** | ● **强于任何产品** | ● 更强 | **这是 Agent 相对产品最大的优势**：产品只会跑固定脚本，Agent 会调试 |
| ⑧ 凭据 / 许可 / 一机一码 | ○ 不能，也不该 | ○ 仍然不能 | 这是制度问题，不是智力问题 |

**结论：除了"点 GUI 下一步"和"处理授权"，Agent 今天就能干完一个技术用户的迁移，而且干得比产品好——因为它能修。**

这一点非常重要：**产品是"预设路径"，Agent 是"现场排障"。而迁移的痛点恰恰全在"预设路径之外"的那 20%。**

## 2. 但"不需要开发软件、不需要商用上线"这个推论，有三处断裂

### 断裂一：用户错配（最容易被忽略）

**能驱动 Agent 完成迁移的人，恰恰是最不需要这个产品的人。**

- 会写 prompt、会开管理员权限、看得懂 PowerShell 报错的人 → 他自己 `winget export` + `chezmoi` 就干完了，甚至不需要 Agent。
- 真正需要"一键搬家"的人（普通用户、设计师、财务、老师）→ 他连"把这段 prompt 贴进哪里"都不知道，更不会在报错时判断该不该继续。

**Agent 把问题解决给了"没有这个问题的人"。**

这是所有"用 Agent 替代产品"的设想最常见的盲区：**Agent 降低的是"能力门槛"，不是"使用门槛"。**

### 断裂二：分发没有消失，只是变薄了

"不用商用上线"是真的省了很多事——不用 EV 代码签名（每年几千到上万）、不用过杀软白名单、不用做安装器、不用上架商店、不用注册公司、不用建客服。**这部分成本确实塌缩了 90%。**

但"把东西送到两台电脑上"这件事没有消失：

- 旧电脑上怎么让 Agent 跑起来？
- 新电脑上怎么让它接着跑？
- 用户怎么知道该信哪个？

**你仍然需要一个"入口"**，只是这个入口从 `.exe` 变成了 `一条命令` / `一个 skill` / `一个 MCP server`。**这不是没有产品，这是产品变薄了。**

### 断裂三：责任没有消失（最硬的一条）

这是我认为**五年内都不会被解决**的一条。

想象一下真实场景：Agent 在新电脑上执行到第 137 步，把一个路径推断错了，`Remove-Item` 删掉了用户的 `Documents`。

- 谁来赔？
- 用户去骂谁？
- 模型厂商会说"这是你自己运行的脚本"；
- Agent 平台会说"这是模型生成的"；
- 而你，如果只是写了个 prompt，**你连被起诉的资格都没有——因为你没有主体**。

**产品存在的意义，有一半不是"功能"，是"有人签字"。** 杀毒软件、备份软件、迁移软件，卖的都不是代码，是"出事了我负责"。

而"负责"这件事，恰恰需要：公司主体、合同、保险、可审计的日志、可回滚的设计、以及一个能被投诉的客服。

**这一块，Agent 一点都没帮你省。**

## 3. 真正的瓶颈不是智力，是"可逆性"

把迁移这件事的特征摊开看，它和当前 Agent 最擅长的任务类型**几乎正交**：

| 迁移任务的特征 | Agent 当前的能力 | 冲突 |
|---|---|---|
| 长时程（几百步、几小时） | 上下文会漂移，长任务容易失焦 | 🔴 |
| 有状态（每一步依赖上一步） | 检查点/回滚能力弱 | 🔴 |
| **不可逆**（删了就是删了） | 没有"撤销"，只会道歉 | 🔴🔴 |
| 需要权限提升（UAC） | 提权后行为不可控 | 🟠 |
| 结果需要"确定性" | 每次运行都不一样 | 🔴 |
| 需要跨两台机器协同 | 多设备编排还很初级 | 🟠 |

**一句话：迁移不是"知识问题"，是"状态变更问题"。**

Agent 是知识机器，迁移是**系统状态机**。知识可以生成，状态变更必须被约束。这就是为什么"Agent 什么都会"和"Agent 能安全地帮你换电脑"之间，隔着一整个工程学科。

**AI 越强，这个矛盾越尖锐**：一个能力更强的 Agent，犯错时的破坏力也更大。所以行业的方向不是"让 Agent 更自由"，而是"给 Agent 加沙箱、加审批、加回滚"——而这些，**全都是产品工作**。

## 4. 三种未来形态

### 情景 A：Agent 全包（概率 25%，2028 年后，仅限技术用户）

技术用户在自己的两台机器上各开一个 Agent，说一句"帮我把环境搬过去"，Agent 自己规划、执行、验证、修复。没有产品，没有公司，没有收费。

- 成立条件：computer-use 成熟 + 沙箱普及 + 长任务可靠性提升。
- 限制：永远停在"技术用户自用"，因为责任无法转移。
- **对你的含义：这块市场你赚不到钱，但你可以成为"那个被加载的 skill"。**

### 情景 B：Agent 是运行时，产品是"技能 + 护栏 + 验证 + 责任"（概率 60%，最可能）

```
Agent（Claude Code / Codex / Cursor / DSH / 本地模型）
        │  加载
        ▼
┌─────────────────────────────────────────┐
│  迁移 Skill（你做的）                     │
│  ├─ SKILL.md        流程与判断规则        │
│  ├─ inventory.ps1   只读采集              │
│  ├─ plan.ps1        生成迁移计划          │
│  ├─ apply.ps1       执行（默认 dry-run）   │
│  ├─ verify.ps1      验证与差异报告        │
│  ├─ policy.yaml     危险操作白名单/黑名单  │
│  └─ evals/          200 个真实换机回放用例 │
└─────────────────────────────────────────┘
```

**你不再写"应用"，你写"技能 + 约束 + 测试集"。**

- 分发：GitHub 仓库、一条 `npx` 命令、一个 MCP server、一个 Claude Code 插件、一个 DSH 插件。
- 成本：从"6 个月 + 3 人 + 签名 + 上架"降到"3 周 + 1 人"。
- **这不叫"不开发软件"，这叫"软件变薄了，但没消失"。**

### 情景 C：迁移这件事本身消失（概率 15%，终局）

Agent 时代真正的终局不是"更好的搬家工具"，而是**"机器变成一份声明"**：

> 你的电脑 = 一份 `machine.yaml`（软件清单 + 配置 + 模型 + 环境）
> 任何一台新机器 + 任何 Agent = 执行这份声明，20 分钟还原

到那时，"迁移"只是"还原"的一个特例，而且旧电脑根本不需要在场。

**这才是"思想超前"的那个版本**：不是 Agent 帮你搬，而是**你根本不需要搬**——你只需要保存一份"你自己"。

## 5. 对你的含义：如果信这个判断，现在该做什么

### 5.1 立刻改掉的一件事：不要先做安装包

按 Agent 路线，你的第一版应该是一个**仓库**，而不是一个 `.exe`：

```
pc-migrate-skill/
├── SKILL.md          ← 给 Agent 读的操作手册（这才是核心资产）
├── scripts/          ← 幂等、可 dry-run 的 PowerShell
├── policy.yaml       ← 哪些操作必须先问人
├─��� evals/            ← 真实换机用例（回放测试）
└── README.md         ← 一条命令的用法
```

用户的使用方式是：

```
旧机：把这段 prompt 贴给 Claude Code / Codex / DSH
新机：把生成的 profile.json 丢给它，说"按这个还原"
```

**发布成本 ≈ 0**：没有签名、没有杀软、没有商店、没有公司。

### 5.2 护城河要重新定义：从"配方库"到"评测集"

既然模型自带配方知识，那"知道怎么装"就不再值钱了。值钱的是：

> **"在这 200 个真实换机场景里，这套流程的通过率是 97%。"**

- 配方库是**公共品**（模型有）；
- 评测集是**私有的**（只有你真的换过 200 台机器才有）。

**Agent 时代，评测（eval）就是新的护城河。** 因为模型能力是所有人的，而"它在你的真实场景里靠不靠谱"只有你有答案。

这也解释了为什么 B 端仍然要买产品：**企业买的不是"能跑"，是"有证据证明它能跑，且出事了有人负责"。**

### 5.3 一个 30 分钟就能做完的实验

不要先写产品，先做这个：

1. 在旧电脑上，让一个 Agent 只做**只读**采集，输出 `profile.json`（软件清单 + 配置路径 + 模型目录 + WSL 信息）。
2. 把 `profile.json` 拿到新电脑，让 Agent 生成 `plan.md`（哪些能自动、哪些要人、哪些不可能）。
3. **看它漏了什么、错在哪。**

**如果它在第 2 步就能给你一份 90% 准确的计划，你的产品形态就已经不是"软件"了。**
如果它错得离谱，那说明"Agent 全包"还早，你还有时间做产品。

这个实验的成本是：一下午 + 两台机器。**它比任何战略讨论都值钱。**

## 6. 反方观点：为什么"Agent 全包"可能永远不会发生在消费级

把话说全，三条反驳：

1. **信任的物理定律**：普通人不会把"格式化硬盘"的权限交给一个会说"抱歉我搞错了"的东西。这不是技术问题，是心理问题，且不随模型变强而消失。
2. **责任无法被自动化**：只要迁移涉及"数据可能丢"，就永远需要一个可被追责的主体。而主体 = 公司 = 产品 = 商用上线。
3. **平台会收编**：如果这条路真能走通，Anthropic/OpenAI/微软会在系统层内置一个"迁移"工具（微软已经试过一次，失败了；但这不排除它再试第三次）。**你的 skill 会被吸进平台。**

| 时间 | 预测 | 可验证信号 |
|---|---|---|
| 2026（现在） | 技术用户可由 Agent 完成 70–85% 迁移，需全程盯 | 你自己跑一遍就知道 |

**注意最后一行：消费级市场不会因为 AI 变强而消失，只会因为 AI 变强而"更便宜、更薄"。**

## 8. 结论

**你的直觉对了一半。**

- **对的一半**：确实不需要"开发一个重型商业软件"。安装包、签名、商店、公司主体这些成本，在 Agent 路线下塌缩了 90%。**这对独立开发者是巨大的解放。**
- **错的一半**：你以为省掉的是"产品"，其实省掉的只是"包装"。**流程、约束、验证、责任，一个都省不掉**——而它们恰恰是产品真正的内核。

所以最聪明的做法不是"用 Agent 替代产品"，而是：

> **把产品做薄，薄到能塞进任何一个 Agent 里；把责任做厚，厚到别人不敢接。**

一句话收尾：

> **Agent 会替你写代码，但不会替你背锅。**
> 而在这门生意里，**背锅才是那个能收钱的部分。**

## 9. 附录：关于"完全权限"的追问

> 追问：现在很多 Agent 在完全权限下，不已经能自动执行电脑上的全部任务了吗？

**先承认：可操作性确实已经不是瓶颈。** Claude Code、Codex CLI、DSH、各种 computer-use agent，在 auto-approve 模式下能跑任意 shell、装任意软件、点任意按钮。"Agent 干不了"这句话在今天不成立。

但"能执行全部操作"和"能可靠完成一次迁移"是两个词：

| 层次 | 解决了吗 | 说明 |
|---|:-:|---|
| 可操作 | ✅ | 全权限下什么都能干 |
| 正确性 | ❌ | 长时程错误累积 |
| 可验证 | ❌ | 常常"报告成功"，实际没成 |
| 可逆性 | ❌ | 删了就是删了 |
| 可追责 | ❌ | 出事找谁 |

### 9.1 错误累积的数学

200 步操作，单步正确率 p，整体成功率 p^200：

| 单步正确率 | 整体成功率（200 步） |
|---|---|
| 99% | ≈ 13% |
| 99.9% | ≈ 82% |
| 99.99% | ≈ 98% |
| 99.995% | ≈ 99% |

迁移是"200 步、每步不能错、错了不能重来"的任务，需要的是最后一行的可靠性。

更麻烦的是**失败是静默的**：产品失败会弹错误框，Agent 失败常常是"已完成 ✅"——配置压根没写进去，它自己也不知道。**迁移最怕的不是报错，是"看起来成了"。**

### 9.2 三个即使全权限也过不去的坎

1. **冷启动。** 迁移发生的那一刻，是新电脑全生命周期里最无能的状态：没软件、没账号、没浏览器，可能连网卡驱动都没有。住在云端的 Agent 无法把自己装到一台还没联网的机器上。这正是手机换机靠"系统内置"而非"下载 App"的原因。
2. **跨机器。** Agent 是"住在一台机器上"的。它对自己那台有全权限，对另一台零权限。迁移天生是两台机器的活，今天没有主流 Agent 能同时握住两台（除非自建 SSH 中继）。**"全权限"的边界是单机的，而迁移是双机的。**
3. **不可恢复错误。** Agent 的强项是"试错重来"，但删旧数据、改分区、覆盖配置没有"重来"。试错循环对可恢复错误是神器，对不可恢复错误是加速器。

### 9.3 最关键的一问：为什么你在自己开发机上敢给全权限？

**不是因为 Agent 变可靠了，是因为环境可以丢弃。** 代码有 git，机器有备份，搞坏了重装。你把"可逆性"外包给了 git 和备份。

> **真正让"全权限"可行的，从来不是模型变聪明，而是"下面垫了一层可以随时丢掉的东西"。**

这把问题从"AI 行不行"翻译成了"基础设施行不行"：

| 场景 | 为什么敢给全权限 | 依赖的基础设施 |
|---|---|---|
| 云端 Agent | 有 VM 快照、disposable sandbox（E2B / Firecracker / Daytona） | 虚拟化 |
| 开发者本机 | 有 git、有备份、坏了重装 | 版本控制 + 重装能力 |
| 普通用户的新/旧电脑 | **什么都没有** | **不存在** |

**结论：未来的方向不是"给 Agent 更多权限"，是"给 Agent 一个可以随便搞坏的环境"。** 而造那个环境——影子盘、快照回滚、双机对拷、原子切换——是产品和基础设施的活，不是模型的活。

### 9.4 由此得到的产品方向：带安全网的迁移

| 方案 | 是否有安全网 |
|---|---|
| 360 换机助手 | ❌ 直接在用户机器上搬 |
| PCmover | ❌ 直接搬 |
| 微软 PC-to-PC | ❌ 直接搬（且已下线） |
| **影子环境 + 快照回滚 + 原子切换** | ✅ **空位** |

> **"敢让 AI 全权干"的前提，是"搞坏了能一键退回去"。谁提供这张安全网，谁收钱。**

Agent 的全权限，解决的是"能不能动手"；迁移要的是"动手之后还能不能收场"。**前者已经免费了，后者还没有人卖。**
