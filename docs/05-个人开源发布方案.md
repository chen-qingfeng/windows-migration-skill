# 个人开源 · Agent Skill 发布方案

> 定位：**个人项目 / 免费 / 开源 / 不承担商业责任**
> 目标：验证"有没有人真的需要它"，而不是"它能不能赚钱"
> 一句话：把商业那一章删掉，剩下的只有一件事——**让人在 60 秒内看到价值。**

---

## 0. 为什么这个定位是对的

| 之前的顾虑 | 在这个定位下 |
|---|---|
| 责任 / 赔偿 | 只读 + as is，**无责任可担** |
| 代码签名 / 杀软白名单 | 不需要安装包，**不经过这条链路** |
| 应用商店 / 上架 | GitHub 就是商店 |
| CAC / 留存 / 低频 | **不适用**——免费工具只看"有没有人用" |
| 护城河 / 商业模型 | **不适用**——你不需要防谁 |
| 团队 / 现金流 | 一个人、业余时间、**可以慢慢做** |

**唯一留下来的真问题：技术上的"最后一公里"仍然存在。** 但免费工具的容错空间大得多——只要诚实标注"这 12 类搬不了"，用户会接受。

## 1. 范围收敛：v0.1 只做"体检"，不做"迁移"

### 1.1 为什么

| 维度 | 迁移 | 体检（只读） |
|---|---|---|
| 上手门槛 | 需要两台电脑 | **一台就够** |
| 风险 | 有 | **零** |
| 失败后果 | 用户流失 | **仍然有用** |
| 可传播性 | 低 | **高（报告可以晒）** |
| 完成度 | 20% | **60%（迁移的第一步）** |
| 开发量 | 3 个月+ | **1–2 周** |

**核心洞察：绝大多数人看到你的仓库时，手边没有第二台电脑。**
任何"需要两台机器"的设计，都会把转化率打到接近零。

### 1.2 那个 60 秒的 aha moment

```
用户对 Agent 说：
  "读一下 https://github.com/<you>/<repo> 的 SKILL.md，按它扫描这台电脑"

Agent 执行只读脚本，输出：
  ┌────────────────────────────────────────┐
  │ 这台机器上发现 87 个可迁移项            │
  │  ├─ 61 个可自动重建（有包管理器来源）   │
  │  ├─ 14 个需要你重新登录/授权            │
  │  ├─ 12 个建议放弃（一机一码/无来源）    │
  │  └─ 约 34 GB 大文件（模型 / WSL / 游戏库）│
  │ 预计还原耗时：约 25 分钟                │
  └────────────────────────────────────────┘
```

这份报告本身就是产品。**它可截图、可分享、可引发"你漏了我的 XX"的 issue——而这正是你要的传播。**

## 2. 仓库长什么样

```
pc-handover/                     ← 名字待定，见 §6
├── README.md                    ← 第一屏必须是一句话 + 一张报告截图
├── SKILL.md                     ← ★ 核心资产：给 Agent 读的操作手册
├── LICENSE                      ← MIT
├── profile.schema.json          ← 输出格式的契约
├── scripts/
│   ├── inventory.ps1            ← 只读采集（不写、不删、不提权）
│   ├── classify.ps1             ← 归类：可自动 / 需人工 / 搬不了
│   └── report.ps1               ← 生成 Markdown 报告
├── examples/
│   ├── profile.example.json
│   └── report.example.md        ← 直接拿这个当 README 的截图
└── evals/
    ├── cases/                   ← 真实机器的脱敏样例
    └── run.ps1                  ← 回放测试：改了脚本，结果不能倒退
```

### 2.1 `SKILL.md` 才是你的产品

页面会过时，代码会腐烂，**只有 SKILL.md 是 Agent 真正读的东西**。它要写清楚：

1. **什么时候该用**（换机、重装、配新机、复现环境）
2. **安全边界**（只读、不改注册表、不碰凭据、不提权、不联网上传）
3. **执行步骤**（采集 → 归类 → 报告，每步的输入输出）
4. **判断规则**（什么算"可自动"：有 winget/scoop/choco ID；什么算"搬不了"：一机一码、无来源、系统组件）
5. **已知不支持**（诚实列表，这条比功能更影响口碑）
6. **失败时怎么办**（不要重试破坏性操作，直接报告）

**写法建议**：把它当成"写给一个聪明但没见过这台机器的同事"的操作手册，而不是写给机器的文档。

### 2.2 `profile.schema.json` 是契约

```json
{
  "machine": { "os": "Windows 11 24H2", "arch": "x64", "locale": "zh-CN" },
  "apps": [
    {
      "name": "Cursor",
      "source": "winget",
      "package_id": "Anysphere.Cursor",
      "config_paths": ["%APPDATA%\\Cursor\\User"],
      "class": "auto",
      "confidence": 0.95,
      "notes": "需重新登录"
    }
  ],
  "big_files": [
    { "path": "%USERPROFILE%\\.ollama\\models", "size_gb": 18.4, "class": "transfer" }
  ],
  "unmigratable": [
    { "name": "Adobe Photoshop", "reason": "machine_bound_license" }
  ]
}
```

**为什么这个文件重要**：它是"体检"和"还原"之间的桥。有了它，v0.2 才能做"拿着 profile 去新机器还原"，而且**旧机器不需要在场**。

## 3. 三个版本，别一次做完

| 版本 | 内容 | 工作量 | 成功标准 |
|---|---|---|---|
| **v0.1 体检** | 只读采集 + 归类 + Markdown 报告 | 1–2 周 | 有 10 个陌生人贴出自己的报告 |
| **v0.2 还原** | 拿 profile 生成安装脚本（默认 dry-run） | 2–4 周 | 有人真的在第二台机器上跑通 |
| **v0.3 迁移** | 局域网直传 + 校验 | 看兴趣 | 有人提 issue 说"我成功了" |

**关键：v0.1 发布前不要写 v0.2 的代码。** 如果 v0.1 没人用，v0.2 就是白做。

## 4. 发布与传播

### 4.1 README 第一屏（决定 80% 的转化）

```
# <项目名>

把一台 Windows 电脑的"软件 + 配置 + 本地模型"变成一份可还原的清单。
不用两台电脑，不用安装，不写你的磁盘。

## 试一试（60 秒，只读）
把这句话贴给你的 Agent（Claude Code / Codex / Cursor / DSH 都行）：
> 读 https://github.com/<you>/<repo>/SKILL.md，扫描这台电脑并生成迁移报告

## 它会给你什么
[一张真实报告截图]

## 它不会做什么
- 不安装、不删除、不改注册表
- 不读取密码和凭据
- 不承诺"100% 迁移"——搬不了的会明确告诉你
```

### 4.2 渠道（按性价比排序）

| 渠道 | 说明 |
|---|---|
| **GitHub 本身** | 好的 README + 一个 15 秒 GIF，靠 trending 自然获得流量 |
| V2EX / 少数派 | 中文技术社区，对"工具 + 折腾"极其友好 |
| r/ClaudeAI / r/LocalLLaMA | 英文，AI 工具受众，对 skill 类项目接受度高 |
| Hacker News（Show HN） | 一次性爆发，但要有能 30 秒看懂的价值主张 |
| X / 小红书 | 用报告截图传播，比文字有效 10 倍 |

### 4.3 命名建议

要让人一眼知道"这是干什么的"，而不是取一个聪明的名字：

- `pc-handover`（直白）
- `machine-profile`（偏声明式）
- `windows-migration-skill`（偏 SEO）
- `takeover`（短，但太抽象）

**建议：`pc-handover` 或 `windows-migration-skill`。** 前者好看，后者好搜。

## 5. 该衡量什么

| 指标 | 强度 | 说明 |
|---|:-:|---|
| Stars | 弱 | 只能说明"看起来不错" |
| Fork | 中 | 说明有人想改 |
| **Issue** | **强** | "它在我机器上漏了 XX"——这是真用户 |
| **陌生人贴出的真实报告** | **最强** | 证明它在别人的机器上跑起来了 |
| 二次使用 | 极强 | 但免费工具很难测 |

> **100 份别人的真实报告 > 1000 stars。**

所以在 README 里明确请求：「跑完请把你的报告（脱敏后）贴到 Discussions」。这既是社区运营，也是你的数据集。

---

## 6. 三条会让项目死掉的坑

1. **报告不好看。** 纯文本列表没人转发。要花时间把报告做成"能截图发朋友圈"的东西——有数字、有分类、有结论。
2. **想覆盖所有 Windows 版本。** 先只支持 Win11（+ Win10 尽力），其它明确写"未测试"。
3. **想一步做到全自动。** 一旦开始写"自动安装"，你就会掉进"每个软件都要试一遍"的黑洞，而那时你还没有用户。

## 7. 免责与边界（"不想负责"的正确做法）

不是靠一句话免责，是靠**设计上没有可被追责的行为**：

- **LICENSE**：MIT，AS IS，无担保
- **默认只读**：v0.1 全流程不写磁盘
- **不提权**：不请求管理员权限，绕开 UAC 和杀软
- **不联网上传**：所有数据留在本地
- **明确警告**：README 写死"不要用它迁移你唯一的副本"
- **写操作要显式开关**：`--apply`，默认 `--dry-run`

这样你不是"免责"，是**真的没有做过任何破坏性的事**。

---

## 8. 一句话

> **你要证明的不是"我能做出一个迁移工具"，而是"有人愿意花 60 秒试一下"。**
> 前者需要三个月，后者只需要两周——而且只有后者能告诉你该不该继续。
